## Archive the Unfiltered Community Feed

This endpoint accepts a community ID without a keyword. It preserves the
returned feed order for timeline archives, content review, and moderation.

| Feed decision | Request or response field | Archive rule |
| --- | --- | --- |
| Community scope | Path `{id}` | Keep this ID on every exported tweet row. |
| Feed coverage | No `q` parameter | Archive posts without text filtering. |
| Returned order | Response tweet sequence | Preserve the order instead of re-ranking rows. |
| Continuation | `has_next_page` and `next_cursor` | Save each page before advancing. |
| Duplicate control | Tweet `id` | Deduplicate moving-feed pages by stable tweet ID. |
| Saved export | `community_post_extractor` | Produce CSV, JSON, or XLSX timeline files. |

Use community search when reviewers need keywords, `Latest`, or `Top` ranking.

## X Community Tweet Export Questions

### Export Community Tweets

Call `GET /api/v1/x/communities/{id}/tweets` for the recent community feed.
Keep the community ID, Tweet ID, text, author, and creation time. Add replies,
reposts, likes, quotes, media, and cursor state.

Use the community search route when a keyword is required. Feed retrieval
answers what members posted recently. Search answers which posts match a query.

Save each page before advancing `next_cursor`. Deduplicate by stable Tweet ID
when new posts enter the feed during pagination. Record community ID, Tweet ID,
author ID, text, and creation time. Add replies, reposts, likes, quotes, and
media. Keep the page cursor and collection time. Use JSON for application
ingestion. Create CSV or XLSX for analyst handoffs. Label interrupted,
result-capped, or credit-bounded collections as partial.

### What Does the Twitter Community API Return?

The member route returns community profiles. The tweet route returns community
posts and author fields. The info route returns community details. Moderator
and search routes serve their own focused records.

Choose one route per task. Do not combine profile membership and tweet activity
into an ambiguous row. Join them later with stable user and community IDs.

### How Do I Build a Complete Community Tweet Export?

Persist every page before saving `next_cursor`. Deduplicate Tweet IDs when new
posts change the live feed during pagination. Record the collection window.

Use a saved community extraction for CSV, JSON, or XLSX files. Use the direct
route for live pages. Label interrupted or credit-bounded collections as
partial.

## Choose The Community Feed

Use this route for recent posts from one community without a keyword. Use community search routes when the request includes a query. Keep the community ID and cursor with each feed checkpoint.

## Export a Community Timeline Without a Search Query

Request the community feed when analysts need recent posts in timeline order.
Each tweet can include its author, text, replies, reposts, likes, quotes, and
media. Keep the community ID with every exported row.

Store `next_cursor` only when `has_next_page` is true. Send that cursor back
unchanged for the next page. De-duplicate by stable tweet ID when a busy
community receives new posts during pagination.

Use [Live Community Tweet Search](/api-reference/x/community-search)
when the workflow includes specific keywords. Feed retrieval answers what the
community posted recently. Keyword search answers which community tweets match
the supplied query.

For saved CSV, JSON, or XLSX files, create a community extraction job. For a
live dashboard, keep the returned tweet rows and cursor directly. Both paths
should preserve author IDs, timestamps, engagement counts, and media URLs.

## Build a Community Timeline Archive

Choose one community ID and archive window. Request the unfiltered community feed when completeness matters.

Store each Tweet ID, text, author, publication time, and engagement counts. Add media and the returned cursor. Write each page before requesting `next_cursor`.

Deduplicate by Tweet ID. Record the first and last tweet times per page. Label incomplete runs as partial archives.

Use community search separately when the community ID is unknown. This route archives one known community timeline.

## Audit a Cursor-Based Community Feed

Start each feed run with one numeric community ID. Record the request time and
requested `pageSize`. Do not add a keyword to this route. Use community search
when the workflow needs text matching.

Persist every response before advancing its cursor. Store `has_next_page` with
`next_cursor`. Request another page only when the flag is true. Pass the cursor
back unchanged.

Count returned rows and unique Tweet IDs after each page. A busy community can
receive new posts during pagination. Deduplicate repeated Tweet IDs without
discarding richer author, engagement, or media fields.

Keep the first and last tweet timestamps for every run. They describe the
observed feed window. They do not prove a complete historical archive. Label
result caps, credit limits, and interrupted cursors explicitly.

Store a completion record after the final page. Include community ID, page
count, unique Tweet count, first timestamp, and last timestamp. Add collection
time and the interrupted cursor when applicable.

## Preserve Community Tweet Authors and Media

Use one row per stable Tweet ID. Keep author ID, username, profile name, and
verification when returned. Store tweet text and creation time separately from
profile fields.

Keep replies, reposts, likes, and quotes as measured engagement fields. Record
the collection time beside them. Counts can change after the feed run.

Store each media URL with its owning Tweet ID. Keep media type when available.
Do not infer missing images or videos from tweet text. Do not move media URLs
into an author profile column.

Use JSON when an application needs nested authors or media. Use CSV when
analysts need one normalized row. Use XLSX for reviewed spreadsheet handoffs.
Document any column flattening beside the exported file.

Join later profile refreshes through stable author ID. Usernames and profile
names can change. Never replace the original tweet creation time with a profile
refresh time.

## Compare Community Timeline Snapshots

Create a new snapshot ID for every completed feed run. Keep the same community
ID across snapshots. Compare stable Tweet IDs before engagement counts.

Report newly observed tweets separately from changed tweet fields. A missing
Tweet ID may reflect the observed window. It does not prove deletion from X.

Compare authors through stable user IDs. Report username or profile changes as
attributes. Do not treat them as new authors.

Mark every incomplete run before comparison. Exclude partial snapshots from
claims about feed growth or activity. Preserve their rows for troubleshooting
and cursor recovery.

Keep the request time, page count, row count, and completion state. These
fields let another reviewer repeat the comparison without guessing its scope.

## Measure a Community Timeline Window

Define one timeline window before requesting the first page. Record the
community ID and collection start time. This route needs no keyword query.

Save each page before advancing its cursor. Store page number, request time,
first Tweet ID, last Tweet ID, and returned row count. Preserve the exact
cursor used for each request.

After the final page, calculate these concrete measures:

- Unique Tweet IDs collected.
- Earliest and latest tweet creation times.
- Authors represented by stable user ID.
- Tweets containing photos, videos, or animated GIFs.
- Total replies, reposts, likes, and quotes when returned.
- Duplicate Tweet IDs removed after retries.

Label the result as a captured timeline window. Never call it a complete
community archive without separate completeness evidence.

Store the final `has_next_page` value. A false value closes this cursor chain.
A stopped job remains interrupted when another page was available.

## Reconcile a Moving Community Feed

New community tweets can appear while older cursor pages load. Deduplicate all
rows by Tweet ID before export. Keep the newest complete engagement fields.

Do not sort only by page position. Preserve `createdAt` and Tweet ID. Page
boundaries can move between requests while the community remains active.

When a request fails, retain the last durable cursor. Retry with the same
community ID and page size. Never guess, shorten, or decode the cursor.

If a retry repeats a page, compare its Tweet IDs with saved rows. Keep one row
per Tweet ID. Record the repeated request in the collection manifest.

For scheduled snapshots, use separate run IDs. Compare overlaps by Tweet ID.
Report new, repeated, and missing IDs independently.

## Audit Authors, Engagement, and Media

Join authors by stable user ID. Keep usernames and display names as changeable
profile attributes. Never use a visible name as the author key.

Validate every media item against its owning Tweet ID. Preserve its media type
and URL. Do not infer attachments from tweet text.

Keep replies, reposts, likes, quotes, views, and bookmarks in separate columns.
Missing fields stay missing. Never replace unavailable engagement counts with
zero.

Record when each snapshot captured those counts. Engagement can change after
the tweet first appears. Compare counts only with both collection times.

### 400 Invalid community ID

```json
{ "error": "invalid_community_id" }
```
The community ID is empty or invalid.

### 401 Unauthenticated

Anonymous requests get `WWW-Authenticate: Bearer` and a guest wallet checkout action. This is not a Payment challenge.
```json
{ "error": "unauthenticated" }
```
Missing or invalid API key.

### 402 Payment required

Account keys get account options; guest keys get guest top-up only.
No checkout starts automatically. Confirm any payment action.

### 404 Community not found

```json
{ "error": "not_found" }
```
The community could not be resolved. Check the community ID.

### 502 X API unavailable

```json
{ "error": "x_api_unavailable" }
```
The read service returned an error. Retry after a short delay.

### 429 Rate Limit Exceeded

```json
{ "error": "rate_limit_exceeded", "retryAfter": 60 }
```
Your tier rate limit was exceeded. Wait for the `Retry-After` header before retrying.

### 424 Dependency Failed

```json
{ "error": "x_api_unavailable" }
```
The normalized v1 response contract can return 424 when the read service is unavailable.
