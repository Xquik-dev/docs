## Delete an Owned Community, Not a Membership

This endpoint removes the community itself. It requires the community ID and
exact name. Use the leave endpoint to remove only one connected account.

| Deletion gate | Exact evidence | Approval condition |
| --- | --- | --- |
| Community owner | Body `account` | The connected account owns the target community. |
| Community identity | Path `{id}` and body `community_name` | Both values match the reviewed group. |
| Preservation | Community info, rules, and required tweets | The owner saved every required record. |
| Deletion request | Unique `Idempotency-Key` | The key identifies this deletion only. |
| Completion | Response `id`, `status`, and `terminal` | The write action reaches a terminal success state. |

This route does not leave a community membership. It removes the owned group.
Keep the deletion approval separate from member cleanup requests.

## Delete a community cautiously

Use this route only for a community managed by the connected account. Confirm
the numeric community ID before approval. Save the community name,
description, rules, and required records first.

Create a unique idempotency key for this deletion. Reuse it only after a
transport failure. Never share it with a membership or settings action.

Require explicit review for:

- Removing a test community after validation.
- Retiring a community that has completed its purpose.
- Correcting a community created from the wrong account.
- Recording the owner, reason, and approval reference.

Treat the deletion as irreversible within this API workflow. Do not report
success from the request alone. Store the returned action ID and lifecycle
state. Poll the status route when processing remains asynchronous.

| Community deletion record | Request or response source | Completion rule |
| --- | --- | --- |
| Community ID | Path `{id}` | Confirm the exact group before approval. |
| Acting X account | Request `account` | Confirm the connected community owner. |
| Community name | Request `community_name` | Require the confirmation safeguard. |
| Idempotency key | Request header | Reuse it only for an exact replay. |
| Write action ID | Response `id` | Poll the matching lifecycle record. |
| Lifecycle state | Response `status` and `terminal` | Stop only after a terminal state. |
| Stored archive | Community info, tweets, and rules | Preserve required records before deletion. |
| Removal proof | Community info lookup | Expect the community to become unavailable. |

## Archive a Community Before Permanent Removal

Collect each required community record before deletion. Start with
[Community Info](/api-reference/x/community-info). Save the community name,
description, rules, creator, policies, banner, and member count.

Archive community posts with
[Community Tweets](/api-reference/x/community-tweets). Follow every cursor when
the archive requires the complete timeline. Store each tweet ID, author ID,
text, timestamp, and media URL. Also store reply, repost, and like counts.

Export the current roster with
[Community Members](/api-reference/x/community-members). Export moderators
separately with
[Community Moderators](/api-reference/x/community-moderators). Member rows do
not prove moderator roles. Keep both snapshots beside the deletion approval.

| Community archive | API route | Required checkpoint |
| --- | --- | --- |
| Identity and rules | `GET /x/communities/{id}/info` | Community ID, name, creator, rules, and policies |
| Tweet timeline | `GET /x/communities/{id}/tweets` | Every saved cursor page and tweet ID |
| Member roster | `GET /x/communities/{id}/members` | Every saved member page and stable user ID |
| Moderator roster | `GET /x/communities/{id}/moderators` | Moderator user IDs and snapshot time |
| Deletion approval | Internal workflow record | Owner, reason, approver, and community name |

Do not infer a complete archive from one page. Record the final `hasMore`
state for every cursor-based request. Store archive timestamps separately from
the deletion time. Community membership and tweets can change between reads.

## Verify Permanent Community Deletion

Wait for a terminal write result before checking the community. Preserve the
returned action ID, requested community ID, acting account, and final status.

Request the community info route after successful deletion. An unavailable
community confirms removal for this workflow. A temporary read failure does
not prove deletion. Retry the read before sending another write request.

Keep deletion distinct from leaving. Leaving removes one connected account.
Deleting removes the owned community for every member. Never use deletion for
routine membership cleanup.

## Body

<ParamField body="account" type="string" required>

</ParamField>
