## Leave Membership Without Deleting the Community

This endpoint removes one connected account from a community membership. The
community remains available to its other members. It requires no name match.

| Departure check | Exact evidence | Membership outcome |
| --- | --- | --- |
| Departing profile | Body `account` | The intended connected account leaves. |
| Community target | Path `{id}` | The request addresses the reviewed group. |
| Current membership | Pre-departure member lookup | The account belongs to the target community. |
| Departure request | New `Idempotency-Key` | The key differs from the earlier join action. |
| Verification | Community member pages | The account no longer appears when confirmation matters. |

This route does not disband the group. Use community deletion only for an
owned community that should cease to exist.

## Leave a community with context

Use this route after confirming the current community membership. Resolve the
numeric community ID and connected account independently. Save the community
name and approval reference before leaving.

Generate a dedicated idempotency key for this departure. Do not reuse the
earlier join key. Reuse the departure key only for an exact retry.

Community departure workflows often include:

- Leaving a completed event or campaign community.
- Applying a reviewed membership-cleanup request.
- Correcting membership from the wrong connected account.
- Recording the departure time in an account ledger.

Store the action ID and lifecycle state. Keep a failed departure separate from
a confirmed result. Query community members afterward only when independent
verification is required.

| Community departure record | Request or response source | Membership rule |
| --- | --- | --- |
| Community ID | Path `{id}` | Confirm the exact group before leaving. |
| Acting X account | Request `account` | Preserve the departing profile. |
| Community name | Pre-departure lookup | Save the reviewed group name. |
| Idempotency key | Request header | Never reuse the earlier join key. |
| Write action ID | Response `id` | Poll the matching lifecycle record. |
| Lifecycle state | Response `status` and `terminal` | Stop only after a terminal state. |
| Existing tweets | Community tweet archive | Preserve required posts before departure. |
| Departure proof | Community member pages | Confirm the account is absent when required. |

## How to Leave a Twitter Community Through the API

Resolve the numeric community ID before submitting the leave request. Use
[Community Info](/api-reference/x/community-info) to confirm the community
name. Save the connected account that should leave.

Check [Community Members](/api-reference/x/community-members) when current
membership must be proven. Follow every cursor page before declaring the
account absent. A missing profile on one partial page proves nothing.

Send `DELETE /x/communities/{id}/join` with the connected account. Create a
new idempotency key for this departure. Store the returned action ID before
polling its write status.

After terminal success, read the member roster again when verification matters.
Record the verification time and completed cursor. Do not delete the community
to remove one account.

| Membership task | Correct route | Expected result |
| --- | --- | --- |
| Confirm the community | `GET /x/communities/{id}/info` | Name, rules, creator, and policies |
| Confirm current membership | `GET /x/communities/{id}/members` | Connected account appears in a complete roster |
| Leave the community | `DELETE /x/communities/{id}/join` | One connected account leaves |
| Rejoin later | `POST /x/communities/{id}/join` | The connected account requests membership again |
| Delete an owned community | `DELETE /x/communities/{id}` | The entire community is removed |

Use this community membership API for one account. It preserves the group,
its other members, rules, moderators, and tweet timeline.

## Reconcile Community Membership After Leaving

Keep the leave receipt separate from later roster snapshots. The receipt
records the requested action. The roster records membership observed later.

Store the community ID, connected account, action ID, terminal state, and
verification timestamp. A later rejoin creates a new action and idempotency
key. Never overwrite the earlier departure record.

If the account still appears after terminal success, refresh the complete
roster once. Preserve the unexpected result and request ID. Do not submit
parallel leave requests with different keys.
