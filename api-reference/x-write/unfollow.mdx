## End an outbound follow

Use this route when the connected account should stop following one profile.
Resolve the target user ID from the existing relationship record. Confirm the
acting account separately. This avoids reversing another account’s follow.

Create a fresh idempotency key for the unfollow. Never reuse the earlier follow
key. Reuse this key only after an interrupted request.

Unfollow workflows commonly include:

- Removing profiles from a completed campaign.
- Applying an approved account-cleanup list.
- Reversing a follow made from the wrong connected account.
- Reconciling outbound relationships with a CRM decision.

Store the action ID and returned lifecycle state. Do not confuse unfollowing
with removing a follower. The remove-follower route changes an inbound
relationship instead.

## Review a Following-Cleanup Batch

Resolve every target to an X user ID before sending unfollow requests. Keep
the username only as a reviewer-friendly label. The path requires the stable
user ID.

Create one approval row per outbound relationship. Include the acting account,
target user ID, target username, reason, and approval reference. Never reuse
one row for several targets.

Generate a separate idempotency key for every approved unfollow. Reuse that
key only when retrying the identical request. A different target requires a
different key.

Submit cleanup rows independently. Store each returned action ID immediately.
One failed action must not erase completed results from the same batch.

Poll non-terminal actions before reporting completion. Classify final results
as completed or failed. Keep retryable transport failures separate from final
action failures.

Do not infer an unfollow from a missing profile in an earlier export. Resolve
the intended target and preserve the decision source. Profile availability and
following state are different facts.

Use the correct route for each relationship change:

- Unfollow removes whom the connected account follows.
- Remove follower ends one inbound relationship to the connected account.
- Unretweet removes one repost and keeps follow relationships unchanged.
- Tweet deletion removes a post and does not modify following.

Finish the batch with target counts, completed actions, failed actions, and
stored action IDs. This gives reviewers a precise following-cleanup audit.

| Unfollow batch column | Source | Cleanup rule |
| --- | --- | --- |
| `batch_id` | Integration value | Group one approved following-cleanup run. |
| `acting_account` | Request `account` | Keep relationship changes isolated by connected account. |
| `target_user_id` | Path `id` | Use the stable numeric target ID. |
| `target_username` | Review context | Keep a readable label without using it as the key. |
| `reason` | Approval row | Preserve why this outbound relationship should end. |
| `idempotency_key` | Request header | Generate one unique key per target. |
| `write_action_id` | Response `id` | Store immediately for independent polling. |
| `status` | Response `status` | Classify queued, completed, and failed rows. |
| `terminal` | Response `terminal` | Count completion only after a terminal state. |

| Relationship change | Correct route | What changes |
| --- | --- | --- |
| Stop following a profile | `DELETE /x/users/{id}/follow` | One outbound following relationship |
| Remove an account follower | `POST /x/users/{id}/remove-follower` | One inbound follower relationship |
| Remove a repost | `DELETE /x/tweets/{id}/retweet` | Repost state only |
| Delete a tweet | `DELETE /x/tweets/{id}` | One post, not follower or following state |
