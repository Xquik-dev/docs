## Publish a repost deliberately

Use this route to repost one known tweet from a connected account. Resolve the
tweet ID before the approval step. Show the tweet text, author, and media to
the reviewer. This gives the reviewer enough context before distribution.

Assign a unique idempotency key to that repost decision. Reuse it only when
the same network request needs recovery. Store the action ID with the source
tweet ID and acting account.

Repost workflows often include:

- Amplifying an approved announcement from a partner account.
- Reposting a customer reply selected by a support team.
- Sharing a monitored tweet after a moderation checkpoint.
- Preventing two workers from reposting the same tweet.

Do not assume an accepted request already changed the account timeline. Read
the lifecycle state. Poll the status endpoint when the action remains queued.

| Repost action column | Source | Distribution rule |
| --- | --- | --- |
| `acting_account` | Request `account` | Keep the connected account with the repost decision. |
| `tweet_id` | Path `id` | Use the exact source Tweet ID approved for distribution. |
| `source_author_id` | Review context | Preserve the original tweet author when available. |
| `approval_reference` | Workflow value | Link the repost to its campaign or moderation decision. |
| `idempotency_key` | Request header | Generate one key for this account and Tweet ID. |
| `write_action_id` | Response `id` | Store the durable repost action before polling. |
| `status` | Response `status` | Keep queued, completed, and failed reposts distinct. |
| `terminal` | Response `terminal` | Mark distribution complete only when `true`. |
| `requested_at` | Integration timestamp | Audit when the repost request was submitted. |

| Repost outcome | Evidence | Campaign action |
| --- | --- | --- |
| Queued | `terminal: false` | Poll `statusUrl`; do not count the repost yet. |
| Completed | Terminal success | Record the account, source Tweet ID, and completion time. |
| Already reposted | Converged terminal result | Complete without another repost request. |
| Retryable failure | `safeToRetry: true` | Preserve the receipt and follow lifecycle guidance. |
| Final failure | Terminal failure | Store the error and exclude the repost from completed totals. |

## Choose a Repost or New Tweet

Use a repost when the account should share an existing tweet unchanged. The
request needs the source tweet ID and connected account. It creates no new
caption or reply text.

Use [Create Tweet](/api-reference/x-write/create-tweet) for original posts,
replies, or media captions. A reply needs `reply_to_tweet_id`. A repost uses
this endpoint instead.

| Publishing intent | API route | Required content |
| --- | --- | --- |
| Share an existing tweet unchanged | `POST /x/tweets/{id}/retweet` | Source tweet ID and connected account |
| Publish original text | `POST /x/tweets` | New tweet text and connected account |
| Reply to a tweet | `POST /x/tweets` | Reply text and `reply_to_tweet_id` |
| Remove a repost | `DELETE /x/tweets/{id}/retweet` | Source tweet ID and connected account |

Show the source tweet during approval. Include its author, text, media, and
current availability. Do not substitute a search result's position for its
stable tweet ID.

## Reconcile Retweet Automation

Store one receipt per connected account and source tweet. This key prevents
two workers from counting the same repost as separate campaign results.

Keep queued, completed, already-reposted, and failed outcomes distinct. An
already-reposted outcome satisfies the requested state. It does not create a
second repost.

Use [Unretweet](/api-reference/x-write/unretweet) for an approved rollback.
The rollback needs a new idempotency key. Preserve both action IDs so the
campaign record shows distribution and later removal.

</ParamField>

</ParamField>

## Path parameters

<ParamField path="id" type="string" required>
  The ID of the tweet to retweet.
</ParamField>

## Body

<ParamField body="account" type="string" required>
