## Remove a like safely

Use this route when a connected account must reverse an existing like. Verify
the tweet ID against your engagement ledger first. Also verify the connected
account that created the original like. Those checks prevent unrelated
engagement from being removed.

Create one idempotency key for the intended unlike. Reuse it after transport
failures only. Never share that key with the earlier like request. Confirm the
returned action state before updating your local record.

Useful unlike workflows include:

- Reversing an engagement decision after human review.
- Removing a like when a campaign rule changes.
- Reconciling a queue with the current liked state.
- Recording who requested the removal and when.

Treat a missing or inaccessible tweet as a separate outcome. Preserve the
tweet ID, account identity, response status, and action ID for investigation.

## Confirm Like Removal

Store the Tweet ID, connected account ID, action ID, and request time. Keep the idempotency key. Poll the write status until it reaches a terminal state.

A queued response does not prove removal. An already-unliked result means the like state converged.

Refresh the liked-tweets view only when downstream work requires current proof. Keep read time separate from action time.

Preserve generic errors and request IDs. Then retry the same Tweet. This operation does not change reposts, replies, follows, or bookmarks.
