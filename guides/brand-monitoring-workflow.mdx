Use this workflow when support, marketing, research, or agent pipelines need
fresh X activity. It combines 2 Twitter monitoring tools: account monitors and
keyword monitors. Choose the right Twitter monitoring tool for one profile or
one search query. Monitor Twitter mentions, deliver matching events to a signed
Twitter webhook, and replay stored events.

## Answer Common Twitter Monitoring Questions

### What Is the Best API to Track Twitter Keyword Mentions?

Choose an API storing the exact query and stable event identity. It should
also support receiver recovery. Test a brand name, `@handle`, hashtag,
product, campaign phrase, or Boolean search. Review the Tweet ID, author ID,
text, timestamp, media, and matched query.

Xquik keyword monitors check for matching tweets every 1 second. Each monitor
has its own ID and query. Matching activity becomes a stored event. A signed
webhook can deliver it to a support queue, campaign dashboard, or warehouse.
Use event replay after receiver downtime. Test the query with tweet search
first. Narrow ambiguous terms before paying for continuous monitoring.

### How Do I Monitor a Keyword on Twitter in Real Time?

Create a keyword monitor with `POST /api/v1/monitors/keywords`. Use one focused
Boolean search query for each product, campaign, hashtag, or support topic. The
Twitter keyword monitor checks for matching tweets every 1 second.

Store the monitor ID with its exact query. This keeps later events explainable.
Use the returned event IDs to deduplicate alerts and measure coverage.

Create a webhook that subscribes to the required event types. Verify its
signature, timestamp, and nonce before parsing the body. Save the event before
returning `2xx`. Route events by monitor ID and matched query. Use the events
API to recover stored activity after receiver downtime. Pause an inactive
campaign monitor so it stops producing unnecessary checks.

### Track Keywords Twitter API

Use `POST /api/v1/monitors/keywords` for continuous keyword checks. Keep one
focused query per monitor. Separate brand handles, product names, and support
phrases. Use distinct monitors for campaign hashtags and competitor terms.

Save the monitor ID, exact query, enabled state, and owner. Add its creation
time and expected event types. Test matching tweets before enabling the
monitor. Store stable Tweet IDs and author IDs with received events.
Deduplicate by event ID, not tweet text. Queue rate-limit or receiver failures
for retry. Never create a changed monitor during those retries.

### Twitter Mention Tracking Tool

Use Xquik as a Twitter mention tracking tool. The keyword monitor can track a
brand name, `@handle`, or hashtag. It can also match a campaign phrase or
supported search expression. Marketing teams can route matching tweets to their
own review queues. This routing helps protect brand reputation.

Use precise queries to track Twitter mentions inside relevant online
conversations. Separate mentions of your brand from category research. Connect
Xquik events to broader social listening tools for other networks.

Test the query with tweet search first. Review tweets, replies, authors, and
media before enabling continuous monitoring. Remove terms that attract noise.

Create separate destinations when support, marketing, and research rules
differ. Keep the matching Tweet ID, author ID, text, and timestamp. Add the
query, monitor ID, event ID, and delivery ID. Do not infer sentiment or author
intent without a reviewed downstream classifier. The monitor supplies
matching X activity and replayable delivery evidence.

### Twitter Keyword Monitor

A Twitter keyword monitor watches a stored search expression. Use an exact
brand name, `@handle`, hashtag, campaign phrase, or product name. Supported
Boolean queries can narrow the result. Avoid expressions mixing several
products and owners.

Before enabling it, run the expression through tweet search. Inspect replies,
reposts, author profiles, language, media, and recurring false matches. Save
the approved query with the monitor ID. Subscribe a verified webhook to the
needed event types. Queue received events durably. Deduplicate by event ID.
Pause the monitor after the campaign or investigation ends.

### What Is the Best Way to Monitor a Twitter Account Programmatically?

Create an account monitor with `POST /api/v1/monitors`. Supply the username and
only the event types your receiver needs. Store both `username` and `xUserId`.

The Twitter account monitor API follows new tweets, replies, reposts, and
quotes. It can also detect documented profile changes. Pause the monitor when
the workflow becomes inactive.

Connect the monitor to a signed webhook. Save its ID and stable X user ID. Add
the event type, Tweet ID, event ID, delivery ID, and timestamp. Return `2xx`
only after durable queueing. Replay stored events after receiver downtime. Do
not create duplicate monitors during an uncertain retry. Reuse a matching
account and event configuration.

### Monitor Twitter Mentions

Track an `@handle`, brand spelling, product name, or campaign hashtag. Use a
separate monitor for each support phrase. A handle-only monitor finds explicit
mentions. A brand-name monitor finds references omitting the handle. A
campaign monitor isolates time-bounded work.

Route matched tweets to the responsible queue. Store Tweet ID, author ID,
text, timestamp, matched query, monitor ID, and event ID. Review false matches
before broadening the query. Add downstream labels only after a human or tested
classifier reviews the tweet. Use stored event replay after webhook downtime
instead of depending on receiver availability.

### Twitter Webhook Alerts

Create a webhook endpoint for the exact monitor event types your application
handles. Verify `X-Xquik-Signature`, `X-Xquik-Timestamp`, and
`X-Xquik-Nonce` before accepting the payload. Reject stale timestamps and
replayed nonces according to the documented verification flow.

Queue the payload durably, then return `2xx`. Use `streamEventId` as event
identity and `deliveryId` as the individual receiver attempt. Log monitor ID,
event type, Tweet ID, and queue result without logging secrets. Replay stored
events through `GET /api/v1/events` when a receiver, queue, or warehouse load
fails. Preserve the author ID and matched keyword when present. Also keep the
reply or repost type.

### Twitter Account Monitor API

Use the account monitor API for one known profile. Select only required new
tweets, replies, reposts, quotes, or profile changes. Keep the stable X user ID
beside the username. Usernames can change.

Store monitor ID, enabled state, event types, owner, webhook destination, and
creation time. Deduplicate received activity by event ID. Keep Tweet IDs for
post events. Pause the monitor when the account leaves scope. Use keyword
monitors for broad terms spanning many accounts. Avoid long lists of unrelated
account monitors.

### How Do I Get Real-Time Twitter Alerts via Webhook?

Create a receiver with `POST /api/v1/webhooks`. Subscribe it to the same event
types as the account or keyword monitor. Verify every signature before reading
the event.

Return `2xx` after durable queueing. Use `streamEventId` for event identity and
`deliveryId` for each receiver attempt. These Twitter webhook alerts remain
recoverable through stored event replay. They provide instant alerts without
making receiver uptime the only recovery path.

Test the complete path with a noncritical monitor. Reject signature failures.
Keep duplicate deliveries idempotent. Confirm a stored event can be replayed.
Record monitor ID, event ID, delivery ID, and event type. Add Tweet ID,
receive time, and queue result. Keep API keys and webhook secrets outside
payload logs. Queue downstream retries after acknowledging a valid delivery.

## Plan a Brand Monitoring Scope

Teams comparing social media monitoring tools can use Xquik for X-specific
monitoring. It returns tweets, replies, profiles, and monitor events.

Start brand monitoring with one documented question. A support team may need
new complaints. Marketing may need campaign mentions. Research may need posts
from known competitors. Each question requires a different monitor.

Use an account monitor for one known profile. Track new posts, replies, quotes,
reposts, or documented profile changes. Keep the stable X user ID beside the
username. Usernames can change after monitoring begins.

Use a keyword monitor for text that can appear across many profiles. Choose a
brand name, product name, handle, hashtag, campaign phrase, or supported search
expression. Store the exact query with every monitor ID.

Do not combine unrelated products inside one broad query. Separate monitors
produce clearer events and simpler routing rules. They also let teams pause one
campaign without stopping other brand alerts.

Define the receiving team before monitor creation. Record whether support,
marketing, research, or an agent owns each event. This ownership prevents the
same Twitter mention from entering several unmanaged queues.

Write the required event types beside the monitoring goal. Remove event types
that no receiver uses. A narrow event contract reduces unnecessary webhook
traffic and review work.

## Create an Account Monitor

Use an account monitor when the workflow tracks an owned account, creator,
competitor, customer, or partner. Choose only the event types the receiver will
process.

```bash
curl -X POST https://xquik.com/api/v1/monitors \
  -H "x-api-key: xq_YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "username": "username",
    "eventTypes": ["tweet.new", "tweet.reply", "profile.bio.changed"]
  }' | jq
```

Store the returned `id`, `username`, `xUserId`, `eventTypes`, `isActive`,
`createdAt`, and `nextBillingAt` with the brand workspace.

## Create a Keyword Monitor

Use a keyword monitor when the trigger is a search query instead of one account.
Keep the query under 512 characters, then store the returned monitor ID with
the exact query used.

```bash
curl -X POST https://xquik.com/api/v1/monitors/keywords \
  -H "x-api-key: xq_YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "query": "\"Xquik\" OR @username",
    "eventTypes": ["tweet.new", "tweet.reply"]
  }' | jq
```

Keyword monitors are best for campaign names, product launches, support terms,
and category discovery. Account monitors are better when every event should be
anchored to one known profile.

## Write Focused Twitter Monitoring Queries

A useful query describes one recognizable conversation. Include the brand,
product, campaign, hashtag, or handle that reviewers actually understand.
Preserve the query exactly after creation.

Use quoted phrases when word order matters. Use a handle when direct mentions
matter. Use a hashtag when a campaign publishes one. Combine terms only when
they share the same business intent.

Test the query with tweet search before starting continuous monitoring. Review
returned tweets, replies, authors, media, and engagement counts. Remove terms
that attract unrelated conversations.

Keep separate queries for product support and industry research. Support needs
specific complaints, account mentions, and reply context. Research often needs
broader category terms and longer review windows.

Version material query changes. Store the old monitor ID, old query, replacement
monitor ID, and change time. This protects comparisons across campaign periods.

Do not rewrite historical events after changing a query. Earlier events reflect
the search expression active at their event time. New events belong to the
replacement or updated monitor contract.

Review high-volume queries before enabling more receivers. A precise Twitter
monitoring tool should produce actionable tweets. Avoid unbounded streams of
generic words.

## Deliver Events to a Webhook

Create one webhook per receiver boundary. Store the returned `secret` once, then
verify every request before parsing or queueing the event.

```bash
curl -X POST https://xquik.com/api/v1/webhooks \
  -H "x-api-key: xq_YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://example.com/xquik/brand-monitor",
    "eventTypes": ["tweet.new", "tweet.reply", "profile.bio.changed"]
  }' | jq
```

Webhook payloads include `deliveryId`, `streamEventId`, `eventType`, `timestamp`,
and `data`. Return `2xx` after signature verification and durable enqueueing.
Use `deliveryId` for receiver retry de-dupe and `streamEventId` for event
de-dupe across webhook endpoints.

## Route Real Time Alerts to the Right Team

Map each event type to one receiver action. New tweets may enter a research
queue. Replies may enter support triage. Profile changes may enter an account
review workflow.

Verify every Twitter webhook before reading its event. Reject invalid
signatures, stale timestamps, and reused nonces. Store the accepted delivery
before running enrichment or classification.

Use `streamEventId` as the event identity across webhook endpoints. Use
`deliveryId` for one receiver attempt. Keeping both IDs prevents duplicate
alerts during retries.

Return a successful response after durable enqueueing. Do not wait for slow
profile lookups, media downloads, CRM writes, or agent analysis. Process those
steps from the queue.

Keep raw signing values outside shared tables. Store the verification result,
event type, tweet ID, author ID, monitor ID, and received time. These fields
support later audits without exposing authentication material.

Define escalation rules outside the webhook handler. A support service can
route reply events by product. Marketing can route campaign posts by query.
Research can retain events without notifying a person.

Real time alerts still need replay. Receiver downtime, deployments, and queue
failures can interrupt webhook handling. Stored events provide the recovery
path.

## Replay Stored Events

Use stored events as the recovery lane after failed receiver deploys, queue
outages, or warehouse backfills. Filter by the monitor type you are replaying.

```bash
curl "https://xquik.com/api/v1/events?monitorId=42&eventType=tweet.new&limit=50" \
  -H "x-api-key: xq_YOUR_KEY_HERE" | jq
```

```bash
curl "https://xquik.com/api/v1/events?keywordMonitorId=21&eventType=tweet.new&limit=50" \
  -H "x-api-key: xq_YOUR_KEY_HERE" | jq
```

Store `hasMore` and `nextCursor`. Pass `nextCursor` back as `after` only when
`hasMore` is true.

## Add Search Backfill

Monitors catch activity after creation. Use search or mention reads when the
brand workspace needs historical context before the monitor starts producing
events.

```bash
curl "https://xquik.com/api/v1/x/tweets/search?q=%22Xquik%22%20OR%20%40username&limit=50" \
  -H "x-api-key: xq_YOUR_KEY_HERE" | jq
```

```bash
curl "https://xquik.com/api/v1/x/users/username/mentions?limit=50" \
  -H "x-api-key: xq_YOUR_KEY_HERE" | jq
```

Keep backfill rows separate from monitor events so dashboards can distinguish
historical search results from live webhook deliveries.

## Measure Brand Monitoring Coverage

Count stored events by monitor ID, query, event type, and collection window.
Keep account-monitor events separate from keyword-monitor events. This prevents
one active profile from distorting broader brand mention counts.

Track unique tweet IDs and unique author IDs. Event counts alone can overstate
activity when several receivers process the same event. Deduplicate with
`streamEventId` before calculating reporting totals.

Xquik returns tweets, replies, authors, profiles, media, and monitor events. It
does not return a calculated share of voice. Build that metric downstream from
clearly defined brand and comparison queries.

Build Twitter analytics downstream from unique tweet IDs and event windows.
Keep social media management approvals outside the monitor receiver.

For share of voice, record every included query and time window. Count unique
matching tweets for each brand. Divide one brand's count by the combined count.
Do not mix incomplete backfills with complete monitor windows.

Treat sentiment analysis as a separate classification step. Preserve the
original tweet text and classifier version. Never replace the returned post
with only a positive, neutral, or negative label.

Report delivery health separately from conversation volume. A high tweet count
does not prove every Twitter webhook succeeded. Compare stored event IDs with
delivery records for transport coverage.

Label partial windows clearly. A paused monitor, exhausted credits, failed
backfill, or receiver outage can change the observed total. Store those states
beside every report.

## Build a Brand Mention Triage Queue

Create one review item from each verified event. Show the tweet text, author,
creation time, event type, matching query, and source monitor. Keep the tweet
ID available for replies, threads, and profile lookups.

Support reviewers need concrete context. Show whether the event is a new tweet,
reply, quote, repost, or mention. Link related replies or thread context only
after the reviewer requests them.

Use explicit queue states. New items await review. Assigned items identify an
owner. Resolved items store the decision time. Ignored items retain a reason.

Never use visible row order as identity. New events can change the queue order.
Store reviewer decisions against `streamEventId` and tweet ID.

Route product questions by the keyword monitor query. Route account-specific
activity by account monitor ID. Keep routing rules readable so operators can
explain why a post reached their team.

Avoid automatic public replies from a brand monitoring event. Review the tweet,
author, conversation, and connected account first. X write actions need their
own approval and idempotency key.

Keep a replay checkpoint for every queue. Store the last completed cursor only
after all returned events are durable. Resume with `after` when `hasMore` is
true.

Measure queue latency from event time to first review. Measure delivery latency
separately. These timings identify whether monitoring, transport, or human
review caused a delay.

## Maintain Account and Keyword Monitors

Review active monitors on a regular schedule. Confirm the owner, purpose,
query, event types, receiver, and next billing time. Pause monitors that no
longer serve an active workflow.

Check account monitor identity with both username and X user ID. A renamed
profile should remain tied to the stable ID. A different target requires a new
monitor.

Review keyword queries after launches, incidents, and campaign changes. Remove
expired terms. Separate a new product name into its own monitor when routing or
reporting differs.

Compare each monitor's event types with webhook subscriptions. Missing webhook
types prevent expected alerts. Extra webhook types create receiver work that
the monitoring plan did not request.

Test the receiver after configuration changes. Verify a signed delivery, queue
write, event identity, and replay lookup. Keep the result with the change
record.

Check credits before resuming several monitors. Active account and keyword
monitors consume credits each hour. Record `nextBillingAt` for budget alerts.

Delete a monitor only when its query or account should stop permanently. Export
required event and delivery evidence first. Use pause when a team expects to
resume the same monitor later.

Document every material change. Store the monitor ID, earlier state, new state,
operator, reason, and change time. This history keeps brand monitoring reports
understandable.
