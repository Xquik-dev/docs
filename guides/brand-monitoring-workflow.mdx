Use this Twitter monitoring API for support, marketing, research, or agent
pipelines. It handles fresh X activity. It combines 2 Twitter monitoring tools:
account monitors and keyword monitors. Choose the right Twitter monitoring tool
for one profile or one search query. Monitor Twitter mentions, deliver matching
events to a signed Twitter webhook, and replay stored events.

Use one keyword monitor to monitor Twitter keywords and campaign phrases. Use
one account monitor to monitor Twitter account activity from a known profile.

## Build a Real Time Twitter Monitoring Workflow

Xquik monitors X only. Connect other social media platforms through separate
social listening tools. Use one social media strategy across those workflows.

Xquik returns matching tweets, replies, profiles, media, and monitor events.
It does not classify sentiment. Review sentiment in a downstream system.

During a free trial comparison, test each tool with the same queries. Compare
matching Tweet IDs, author IDs, timestamps, webhook delivery, and event replay.
Historical data should contain saved tweets, replies, profiles, and monitor
events. Track specific handles, hashtags, products, and campaign phrases.
Use real time Twitter monitoring for active campaigns and support terms. Keep each
keyword and hashtag in a separate monitor. When tracking brand mentions, store
Tweet IDs, author IDs, timestamps, and matched queries. Analyze data fields
such as replies, reposts, likes, profiles, media, and monitor events.

## Answer Common Twitter Monitoring Questions

### What Is the Best API to Track Twitter Keyword Mentions?

Choose an API that stores the exact query and stable event IDs. Test one brand
name, @handle, hashtag, product, or campaign phrase. The
Twitter keyword monitor checks for matching tweets every 1 second. Review each Tweet ID, author ID,
text, timestamp, media, and matched keyword. Send matching events through a
signed webhook. Queue each event before acknowledging delivery. Replay stored
events after receiver downtime. Compare the same query across tools. This test
reveals missed tweets, duplicate events, and delayed alerts.

### How Do I Monitor a Keyword on Twitter in Real Time?

Create a keyword monitor with `POST /api/v1/monitors/keywords`. Use one Boolean
query for each product, campaign, hashtag, or support topic. Store its monitor
ID and exact query. Test the keyword against recent tweets first. Inspect reply,
author, language, and media fields. Subscribe a webhook to required event types.
Verify its signature, timestamp, and nonce. Save each event before returning
`2xx`. Replay stored events after receiver downtime. Pause inactive campaign
monitors to stop unnecessary checks.

### Track Keywords Twitter API

Use `POST /api/v1/monitors/keywords` for continuous keyword checks. Separate
brand handles, products, support phrases, campaign hashtags, and competitor
terms. Save the monitor ID, query, owner, event types, and enabled state. Test
matching tweets before enabling the monitor. Store each Tweet ID and author ID.
Deduplicate webhook deliveries by event ID. Queue rate-limit or receiver
failures for retry. Never create a changed monitor during those retries. Pause
the keyword monitor after its campaign ends.

### Twitter Mention Tracking Tool

Use Xquik as a Twitter mention tracking tool. Track a brand name, @handle,
hashtag, misspelling, competitor, pain point, or industry term.
Marketing teams can route matching tweets to their own review queues.
This routing helps protect brand reputation.
Use precise queries to track Twitter mentions inside relevant online
conversations. Review each tweet, reply, author, and media attachment. Store the
matched keyword, monitor ID, event ID, and delivery ID. Connect
Xquik events to broader social listening tools for other networks. Review
sentiment and author intent downstream.

### Twitter Keyword Monitor

A Twitter keyword monitor watches one stored search expression. Use an exact
brand name, @handle, hashtag, campaign phrase, or product name. Boolean operators
can remove known false matches. Test the keyword with tweet search first. Review
tweets, replies, reposts, author profiles, languages, and media. Save the
approved query beside its monitor ID. Subscribe a verified webhook to required
event types. Queue received events durably. Deduplicate every delivery by event
ID. Pause the monitor after its campaign or investigation ends.

### What Is the Best Way to Monitor a Twitter Account Programmatically?

Create an account monitor with `POST /api/v1/monitors`. Supply one username and
required event types. Store its stable X user ID and monitor ID.
The Twitter account monitor API follows new tweets, replies, reposts, and quotes. It also
detects documented profile changes. Deliver each event through a signed webhook.
Queue the payload before returning `2xx`. Deduplicate deliveries by event ID.
Replay stored events after receiver downtime. Reuse the same monitor during
uncertain retries. Pause profiles that leave the monitoring scope.

### Monitor Twitter Mentions

Track an @handle, brand spelling, misspelling, product, or campaign hashtag. A
handle query finds explicit mentions. Brand keywords find untagged references.
Campaign queries isolate time-bounded work. Test every query with tweet search.
Review tweets, replies, authors, profiles, and media before continuous checks.
Route each matching event to the responsible queue. Store Tweet ID, author ID,
timestamp, query, monitor ID, and event ID. Review false matches before
broadening a keyword. Replay stored events after webhook downtime.

### Twitter Webhook Alerts

Create a webhook for the exact monitor event types your application handles.
Verify `X-Xquik-Signature`, `X-Xquik-Timestamp`, and `X-Xquik-Nonce`. Reject
stale timestamps and replayed nonces. Queue the payload, then return `2xx`. Use
`streamEventId` for event identity. Use `deliveryId` for each receiver attempt.
Store monitor ID, keyword, event type, Tweet ID, and author ID. Record the queue
result without logging secrets. Replay stored events after webhook or queue
failures. Deduplicate every retried delivery before alerting reviewers during
outages.

### Twitter Account Monitor API

Use the account monitor API for one known profile. Select required tweets,
replies, reposts, quotes, or profile changes. Store the stable X user ID beside
the username. Usernames can change after monitoring begins. Also store monitor
ID, owner, event types, webhook destination, and active state. Deduplicate each
delivery by event ID. Keep Tweet IDs for post events. Pause accounts that leave
scope. Use keyword monitors for terms spanning many profiles. Avoid unrelated
profiles inside one account-monitor workflow.

### How Do I Get Real-Time Twitter Alerts via Webhook?

Create a receiver with `POST /api/v1/webhooks`. Subscribe it to matching monitor
events. Verify every signature before parsing the event. Queue valid payloads
before returning `2xx`. Use `streamEventId` for event identity. Use `deliveryId`
for each receiver attempt. These Twitter webhook alerts remain recoverable
through stored event replay. They provide instant alerts without making receiver
uptime the only recovery path. Test delivery with a noncritical monitor. Record
monitor ID, event ID, Tweet ID, receive time, and queue result. Store the author
profile ID when present. Never log secrets.

### How Do Businesses Use Twitter Monitoring for Customer Service?

Create one keyword monitor for the brand handle and support phrases. Add one
account monitor for replies to the owned profile. Route matching tweets and
replies into the support queue. Keep Tweet ID, author ID, conversation ID,
query, and event ID. Verify the webhook before queueing each alert. Load thread
context only when an agent opens the item. Record assignment, response decision,
and resolution time. Replay stored events after downtime. Never publish an
automatic reply without account approval.

### How Do I Monitor Competitor Activity on Twitter?

Create separate keyword monitors for each competitor name, handle, product, and
campaign. Use account monitors when every post from one profile matters. Test
each keyword with tweet search before continuous monitoring. Review replies,
reposts, authors, media, and recurring false matches. Route new events to one
research queue. Store the query, monitor ID, Tweet ID, and event ID. Compare
unique tweets across equal collection windows. Label paused or incomplete
periods before reporting changes. Record query changes with timestamps.

### How Do I Integrate Twitter Monitoring Into a Dashboard?

Send verified webhook events to a durable queue. Transform each event into one
dashboard row. Use `streamEventId` as the row's event identity. Show tweet text,
author, query, monitor, event type, and received time. Keep historical search
backfills separate from live monitor events. Calculate totals from unique Tweet
IDs and author IDs. Report delivery failures separately from conversation
volume. Replay missing events before closing a reporting window.
Keep receiver latency beside each delivery status during audits.

### What Are Best Practices for Twitter Monitoring in Crisis Management?

Prepare focused keyword monitors before an incident. Include exact handles,
products, campaign terms, and known misspellings. Assign one incident owner and
one verified webhook receiver. Route matching tweets and replies into a durable
priority queue. Keep Tweet ID, author ID, query, timestamp, and event ID. Review
the full conversation before any public response. Never infer urgency from one
keyword alone. Replay stored events after outages. Pause temporary monitors
after the incident review ends.
Document every monitor change.

## Plan a Brand Monitoring Scope

### Assign One Monitoring Goal

Teams comparing social media monitoring tools can use Xquik for X-specific
monitoring. Start with one documented question. Support may need new complaints.
Marketing may need campaign mentions. Research may need competitor posts.

### Choose One Monitor Type

Use an account monitor for one known profile. Track new posts, replies, quotes,
reposts, or profile changes. Keep the stable X user ID beside the username.

Use a keyword monitor for text that can appear across many profiles. Choose a
brand name, product name, handle, hashtag, campaign phrase, or supported search
expression. Store the exact query with every monitor ID.

### Assign One Receiver

Do not combine unrelated products inside one broad query. Separate monitors
produce clearer events. Assign support, marketing, research, or an agent before
creation. Record required event types. Remove event types that no receiver uses.

## Create an Account Monitor

Use an account monitor for an owned account, creator, or competitor. It also
fits customer and partner profiles. Choose only receiver-supported event types.

```bash
curl -X POST https://xquik.com/api/v1/monitors \
  -H "x-api-key: xq_YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "username": "username",
    "eventTypes": ["tweet.new", "tweet.reply", "profile.bio.changed"]
  }' | jq
```

Store the returned `id`, `username`, `xUserId`, `eventTypes`, `isActive`,
`createdAt`, and `nextBillingAt` with the brand workspace.

## Create a Keyword Monitor

Use a keyword monitor when a search query triggers the workflow. Keep the query under 512 characters.
Store the returned monitor ID with its exact query.

```bash
curl -X POST https://xquik.com/api/v1/monitors/keywords \
  -H "x-api-key: xq_YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "query": "\"Xquik\" OR @username",
    "eventTypes": ["tweet.new", "tweet.reply"]
  }' | jq
```

Keyword monitors are best for campaign names, product launches, support terms,
and category discovery. Account monitors are better when every event should be
anchored to one known profile.

## Write Focused Twitter Monitoring Queries

### Describe One Conversation

A useful query describes one focused conversation. Include the brand, product,
campaign, hashtag, or handle that reviewers know. Preserve the exact query.

Use quoted phrases when word order matters. Use a handle when direct mentions
matter. Use a hashtag when a campaign publishes one. Combine terms only when
they share the same business intent.

### Test Before Monitoring

Test the query with tweet search before starting continuous monitoring. Review
returned tweets, replies, authors, media, and engagement counts. Remove terms
that attract unrelated conversations.

Keep separate queries for product support and industry research. Support needs
complaints, account mentions, and reply context. Research needs broader terms.

Version material query changes. Store the old monitor ID, old query, replacement
monitor ID, and change time. Never rewrite historical events. Review high-volume
queries before adding receivers. Avoid streams built from generic words.

## Deliver Events to a Webhook

Create one webhook per receiver boundary. Store the returned `secret` once, then
verify every request before parsing or queueing the event.

```bash
curl -X POST https://xquik.com/api/v1/webhooks \
  -H "x-api-key: xq_YOUR_KEY_HERE" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://example.com/xquik/brand-monitor",
    "eventTypes": ["tweet.new", "tweet.reply", "profile.bio.changed"]
  }' | jq
```

Webhook payloads include `deliveryId`, `streamEventId`, `eventType`, `timestamp`,
and `data`. Return `2xx` after signature verification and durable enqueueing.
Use `deliveryId` for receiver retry de-dupe and `streamEventId` for event
de-dupe across webhook endpoints.

## Route Real Time Alerts to the Right Team

### Map Events to Queues

Map each event type to one receiver action. New tweets may enter a research
queue. Replies may enter support triage. Profile changes may enter an account
review workflow.

### Verify and Deduplicate

Verify every Twitter webhook before reading its event. Reject invalid
signatures, stale timestamps, and reused nonces. Store the accepted delivery
before adding labels.

Use `streamEventId` as the event identity across webhook endpoints. Use
`deliveryId` for one receiver attempt. Keeping both IDs prevents duplicate
alerts during retries.

### Process Slow Work Later

Return a successful response after durable enqueueing. Process profile lookups,
media downloads, CRM writes, and agent reviews from the queue.

Keep raw signing values outside shared tables. Store the verification result,
event type, tweet ID, author ID, monitor ID, and received time. These fields
support later audits without exposing credentials. Define escalation outside
the handler. Real time alerts still need replay after receiver or queue failures.

## Replay Stored Events

Replay stored events after receiver deploy failures or queue outages. They also
support warehouse backfills. Filter by the monitor type being replayed.

```bash
curl "https://xquik.com/api/v1/events?monitorId=42&eventType=tweet.new&limit=50" \
  -H "x-api-key: xq_YOUR_KEY_HERE" | jq
```

```bash
curl "https://xquik.com/api/v1/events?keywordMonitorId=21&eventType=tweet.new&limit=50" \
  -H "x-api-key: xq_YOUR_KEY_HERE" | jq
```

Store `hasMore` and `nextCursor`. Pass `nextCursor` back as `after` only when
`hasMore` is true.

## Add Search Backfill

Monitors catch activity after creation. Use search or mention reads for earlier
posts. This backfill provides context before new monitor events arrive.

```bash
curl "https://xquik.com/api/v1/x/tweets/search?q=%22Xquik%22%20OR%20%40username&limit=50" \
  -H "x-api-key: xq_YOUR_KEY_HERE" | jq
```

```bash
curl "https://xquik.com/api/v1/x/users/username/mentions?limit=50" \
  -H "x-api-key: xq_YOUR_KEY_HERE" | jq
```

Keep backfill rows separate from monitor events. Dashboards can then distinguish
historical search results from live webhook deliveries.

## Measure Brand Monitoring Coverage

### Count Unique Posts and Authors

Count stored events by monitor ID, query, event type, and collection window.
Keep account-monitor events separate from keyword-monitor events. This prevents
one active profile from distorting broader brand mention counts.

Track unique tweet IDs and unique author IDs. Event counts alone can overstate
activity when several receivers process the same event. Deduplicate with
`streamEventId` before calculating reporting totals.

### Calculate Share of Voice

Xquik returns tweets, replies, authors, profiles, media, and monitor events. It
does not return a calculated share of voice. Build that metric downstream from
clearly defined brand and comparison queries.

Build Twitter analytics downstream from unique tweet IDs and event windows.
Keep social media management approvals outside the monitor receiver.

For share of voice, record every included query and time window. Count unique
matching tweets for each brand. Divide one brand's count by the combined count.
Do not mix incomplete backfills with complete monitor windows.

### Review Sentiment Downstream

Treat sentiment analysis as a separate classification step. Preserve the
original tweet text and classifier version. Never replace the returned post
with only a positive, neutral, or negative label.

### Report Delivery Health

Report delivery health separately from conversation volume. A high tweet count
does not prove every Twitter webhook succeeded. Compare stored event IDs with
delivery records for transport coverage.

Label partial windows clearly. A paused monitor, exhausted credits, failed
backfill, or receiver outage can change the observed total. Store those states
beside every report.

## Build a Brand Mention Triage Queue

### Show Tweet Context

Create one review item from each verified event. Show the tweet text, author,
creation time, event type, matching query, and source monitor. Keep the tweet
ID available for replies, threads, and profile lookups.

Show whether the event is a tweet, reply, quote, repost, or mention. Load related
replies or thread context only when a reviewer requests them.

### Store Review State

Use explicit queue states. New items await review. Assigned items identify an
owner. Resolved items store the decision time. Ignored items retain a reason.

Never use visible row order as identity. New events can change the queue order.
Store reviewer decisions against `streamEventId` and tweet ID.

### Route and Replay

Route product questions by the keyword monitor query. Route account-specific
activity by account monitor ID. Keep routing rules clear.

Avoid automatic public replies from a brand monitoring event. Review the tweet,
author, conversation, and connected account first. X write actions need their
own approval and idempotency key.

Keep a replay checkpoint for every queue. Store the last completed cursor only
after every event is durable. Resume with `after` when `hasMore` is true.

## Maintain Account and Keyword Monitors

### Review Monitor Ownership

Review active monitors on a regular schedule. Confirm the owner, purpose,
query, event types, receiver, and next billing time. Pause monitors that no
longer serve an active workflow.

Check account monitor identity with both username and X user ID. A renamed
profile should remain tied to the stable ID. A different target requires a new
monitor.

### Review Queries and Webhooks

Review keyword queries after launches, incidents, and campaign changes. Remove
expired terms. Separate a new product name into its own monitor when routing or
reporting differs.

Compare each monitor's event types with webhook subscriptions. Missing webhook
types prevent alerts. Extra event types create unnecessary receiver work.

Test the receiver after changes. Verify one signed delivery, queue write, event
identity, and replay lookup.

### Pause Before Deleting

Check credits before resuming several monitors. Active account and keyword
monitors consume credits each hour. Record `nextBillingAt` for budget alerts.

Delete a monitor only when its account or query leaves scope permanently. Export
required events first. Otherwise, pause it. Record the monitor ID, states,
operator, reason, and change time.
